# Reviewer: fable / EVM

Scope: `contracts/evm/src/ProjectEscrow.sol` (`ProjectEscrow`, `EscrowFactory`) at `bbcc87b`, `contracts/evm/script/DeployBase.s.sol`, `contracts/evm/script/DeployBaseSepolia.s.sol`, semantics from `contracts/evm/README.md`, event expectations from `contracts/evm/adapter.ts`. PoC tests: `scratchpad/review/evm/test/FableEscrow.t.sol` (suites `FableEscrowTest`, `FableOddTokenTest`); run with `forge test --root <scratch>/evm --match-contract Fable -vv`. Result: 17 passed, 0 failed (Foundry 1.7.1, solc 0.8.30). Every test named below passed, which for the F-tests means the described behavior was reproduced, not that the code is fine.

## Findings

### F-1: Immutable identity authority with no rotation and no award cancel: a lost or compromised authority key permanently strands every unpaid award whose actor has no active binding
- Severity: High  Confidence: medium
- Location: `ProjectEscrow.sol:38` (`identityAuthority` immutable), `:166` (sole binding path), `:141-154` (no cancel path for awards), `:204-216` and `:220-229` (owner can only reach `freeBalance`), `EscrowFactory.sol:265` (factory-wide immutable authority)
- Description: `bindDestination` is the only function that can ever make an actor payable, and it is gated on a single immutable EOA shared by every vault of the factory. There is no rotation, no multi-party recovery, no award cancellation, and no reserve rescue. Reserved principal and reserved fees can only leave via `pay`. Two failure modes follow. (a) Key loss: every award committed for an actor that has no active binding at that moment can never be paid; its gross stays in `reservedPrincipal` plus `reservedFees` forever and the owner cannot withdraw it. (b) Key compromise: the README's mitigation (delay plus owner cancel) stops theft, but the owner must then cancel every malicious binding, every 48 hours, forever, and honest contributors can never be bound because only the compromised key can bind. The mitigation converts theft into an indefinite lock of the same funds. The README documents the redirect risk and the delay, and lists "operational signer recovery" as a launch gate, but does not state that the vault has no on-chain recovery and that the consequence of loss is permanent reservation of all unpaid awards. The brief's rule "permanent fund lock is High even without theft" applies.
- Scenario: Owner deposits 1,000; commits award A (gross 100) for actor 42 with no binding. Authority key is lost (or stolen; attacker binds actor 42 to itself, owner cancels, repeat). `pay(A, v)` reverts `InvalidBinding` for every v forever. `withdrawUnused(900+1)` and `chargeService(900+1, d)` revert `InsufficientFreeBalance`: the 100 is unreachable by anyone. Multiply by every vault created from the factory, since the authority is a factory-level immutable.
- Evidence: `test_F1_lostAuthorityStrandsUnpaidAwards` PASS: five attacker-bind / owner-cancel rounds over years of warped time; `pay` never succeeds, `reservedPrincipal == 98e6`, `reservedFees == 2e6`, conservation holds throughout.
- Recommendation: Add a constrained recovery path that does not give any single party a new money power, for example: an `owner`-plus-`feeRecipient` (or a factory-held cold key) two-step authority rotation with its own `bindingDelay`, during which the old authority can veto; or allow the owner to re-point an unpaid award's actor only when the actor has had no active binding for N months, under the same delay and with an event. At minimum, state the no-recovery property in the README next to the redirect risk, and make "operational signer recovery" a hard launch gate with an off-chain key-ceremony document.

### F-2: Owner can block an award indefinitely by cancelling every binding version, and an active ("final") binding is stripped by rotation plus cancel
- Severity: Medium  Confidence: high
- Location: `ProjectEscrow.sol:178-185` (`cancelBinding` has no bound, no reason, no distinction between a first binding and a rotation), `:171-173` (rotation overwrites the active binding and restarts the delay)
- Description: The README states "An active binding is final and cannot be cancelled" and "The owner can therefore delay a contributor's payout". Both are weaker than written. (a) Once the authority rotates an active binding (even to the same destination, which the contract allows), the previous active binding no longer exists: `bindings[actorId]` is overwritten with a pending version. The owner can then cancel the pending one, leaving the actor unpayable although it had a final binding minutes earlier. (b) Cancel is one-per-version, but versions are unbounded, so the owner can veto v2, v3, v4 ... forever. The delay is therefore not bounded by anything on chain; it is bounded only by the authority's willingness to keep rebinding and the owner's willingness to keep cancelling. No money moves (the award stays reserved and the owner can never withdraw it), so this is a liveness and documentation finding, not a theft.
- Scenario: Actor 7 bound (v1), 48h pass, v1 active, `cancelBinding(7,1)` correctly reverts. Authority calls `bindDestination(7, sameDest, 1, ...)` → v2 pending. Owner calls `cancelBinding(7,2)`. `pay(id,1)` and `pay(id,2)` revert forever. Authority binds v3 ... v12; owner cancels each; `pay` still reverts.
- Evidence: `test_F2_activeBindingLostAfterRotateAndCancel` PASS (ten consecutive versions cancelled, `paid == false`).
- Recommendation: Keep the previous active binding payable while a rotation is pending (store `activeDestination`/`activeVersion` separately from `pendingBinding`, promote on activation, and let `pay` use the active one), so a rotation can only move the destination after the delay and a cancel only drops the pending change. Alternatively cap owner cancels per actor (e.g. two) or require that the cancelled binding's destination differs from the last paid destination. Update the README wording either way.

### F-3: `bindingDelay` is unbounded at the factory; extreme values brick binding (checked overflow) or collide with the `type(uint64).max` cancel sentinel
- Severity: Low  Confidence: high
- Location: `ProjectEscrow.sol:172` (`uint64(block.timestamp) + bindingDelay`), `:183` (sentinel), `EscrowFactory.sol:272-282` (no bound check), `:116` (no bound check)
- Description: The constructor accepts any `bindingDelay`. If it is large enough that `uint64(block.timestamp) + bindingDelay` exceeds `uint64`, `bindDestination` reverts with an arithmetic panic for every actor in every vault of that factory, which is a permanent lock of all awards (no binding can ever exist). If it is exactly `type(uint64).max - block.timestamp`, the binding is created with `activatesAt == type(uint64).max`, indistinguishable from a cancelled binding, so `pay` never succeeds. Both deploy scripts hard-code 48 hours and `escrow-policy.mjs` enforces a minimum off chain, so there is no realistic path to this in the current deployment, but the contract itself has no upper bound and `bindingDelay == 0` is also accepted (no veto window).
- Scenario: Registrar deploys `EscrowFactory(..., type(uint64).max)`; every `bindDestination` reverts. Or `delay = 2^64-1-now`; binding is born cancelled.
- Evidence: `test_F3a_hugeDelayBricksBinding` PASS (generic revert, not `InvalidBinding`), `test_F3b_sentinelCollision` PASS (`activatesAt == type(uint64).max` after a fresh bind).
- Recommendation: In `EscrowFactory`'s constructor require `bindingDelay_ >= 48 hours && bindingDelay_ <= 30 days` (or similar), so the on-chain artifact carries the policy. Use an explicit `cancelled` bool instead of the sentinel.

### F-4: `cancelBinding` is idempotent on an already-cancelled version and re-emits `BindingCancelled`
- Severity: Low  Confidence: high
- Location: `ProjectEscrow.sol:180` (`block.timestamp >= binding.activatesAt` is false when `activatesAt == type(uint64).max`)
- Description: After a cancel, `activatesAt` is the sentinel, so the "already active" guard never fires and the owner can call `cancelBinding(actorId, sameVersion)` any number of times, at any later time, each emitting a fresh `BindingCancelled(actorId, version)`. State is unchanged, so no funds effect, but an indexer that counts cancel events per version, or that keys on the cancel transaction, sees duplicates.
- Scenario: `bind(9)`, `cancelBinding(9,1)`, warp 20 days, `cancelBinding(9,1)` twice more; all succeed.
- Evidence: `test_F4_cancelIsIdempotentAndReemits` PASS.
- Recommendation: Add `|| binding.activatesAt == type(uint64).max` to the revert condition (or the explicit bool from F-3).

### F-5: `chargeService` moves any amount of free funds to the fee recipient under an owner-chosen digest; "exactly once per invoice" is nominal
- Severity: Informational  Confidence: high
- Location: `ProjectEscrow.sol:220-229`
- Description: The digest is never tied to the amount, to any Slop-signed invoice, or to FND-06's service allocation percentage. The owner can charge the same real invoice twice under two digests, or charge 100% of free funds. All of it goes to `accruedFees` for the immutable fee recipient, so it is not an attacker drain (a compromised owner key already has `withdrawUnused` to itself, which is worse for the sponsor). It does match PAY-10 as written ("only the owner authorizes it", "moves only free sponsor-class funds"). Note for the product side: the contract cannot enforce BOT-11's fee offset or FND-06's cap; those are off-chain promises.
- Evidence: `test_sound_chargeServiceOnlyFreeFunds_andConservation` PASS (600 of 600 free charged under one digest; reserve untouched; duplicate digest rejected).
- Recommendation: Document that digest uniqueness is a client-side property. If a cap is wanted on chain, add a `serviceAllowance` the owner sets at deposit time and check `totalServiceFees + amount <= serviceAllowance`.

### F-6: Registrar can create dead or self-referential vaults; a consumed `projectId` cannot be retired
- Severity: Informational  Confidence: high
- Location: `ProjectEscrow.sol:105-109` (rejects `feeRecipient == this` but not `owner == this` or `identityAuthority == this`), `EscrowFactory.sol:284-294`
- Description: Because the CREATE2 address is predictable, the registrar can pass `owner == vault` (then `refundDestination == vault` passes the equality check): nobody can `deposit` and `sendExact` to self would always revert on the vault-balance check. The factory then records `vaults[projectId]` permanently; there is no way to replace a mis-created vault for that id in this factory, so the project needs a new id or a new factory. Registrar is a documented trust boundary; no funds at risk unless someone transfers tokens directly to the dead vault.
- Evidence: reasoning only.
- Recommendation: Reject `owner_ == address(this)` and `identityAuthority_ == address(this)` in the constructor. Consider a registrar-only `retire(projectId)` that only works while the vault's `totalDeposited == 0`.

### F-7: Minor doc and code mismatches
- Severity: Informational  Confidence: high
- Location: `EscrowFactory.sol:286` (duplicate project reverts with `ProjectEscrow.DuplicateAward`), `ProjectEscrow.sol:164` (`expiresAt` is neither stored nor emitted, so the adapter's `verifyBinding` cannot check it), `script/DeployBase.s.sol:16` (fee recipient comment cites `src/lib/fresh-cycle-policy.mjs`; the address there matches, `0x8f77...9b86`, verified), both scripts do no post-deploy assertion of `factory.token()/feeRecipient()/identityAuthority()/bindingDelay()`.
- Evidence: reasoning only.
- Recommendation: Add a `DuplicateProject` error; emit `expiresAt` or drop it from the ABI note; add `require` lines after deployment in both scripts.

## Checked and found sound

- Reentrancy: `deposit`, `pay`, `withdrawUnused`, `chargeService`, `claimFees` share one `entered` flag (`:88-93`); state is fully updated before `sendExact` in `pay` (`:193-199`) and `withdrawUnused` (`:210-214`); `commitAward`, `bindDestination`, `cancelBinding` make no external calls. A token callback cannot reach owner/authority functions without those keys.
- Exact-transfer enforcement: `deposit` checks the vault delta (`:132-134`); `sendExact` checks both the vault and recipient deltas (`:242-248`). Destination can never equal the vault (`:107-108`, `:168`), so the two balance reads are always on distinct addresses; `destination == feeRecipient` and `destination == owner` behave correctly and fees stay in `accruedFees` until `claimFees` (`test_sound_destinationEqualsFeeRecipientOrOwner` PASS). Fee-on-transfer or rebasing tokens cause a clean revert, no drift.
- `callToken` (`:251-256`): empty return accepted (USDT-style), 32-byte `true` accepted, 64 bytes rejected, non-bool word rejected via `abi.decode` revert (`test_sound_callTokenReturnData` PASS). Combined with the balance checks, silent-failure tokens cannot inflate counters.
- Binding lifecycle: no instant allows both `cancelBinding` and `pay` (cancel needs `now < activatesAt`, pay needs `now >= activatesAt`, `:180`, `:191`); a cancelled binding can only be replaced by a new version (`:173` overwrites the full struct), never un-cancelled; a cancel cannot target a non-existent or future version (`:180`), so pre-blocking is impossible; stale `pay(id, oldVersion)` fails after rotation (`:191`); first binding must use `expectedVersion == 0` and versions are strictly sequential (`:169-171`). Tests: `test_sound_cancelledBindingNeverPays_andBoundaryInstants`, `test_sound_rotationInvalidatesStalePay`, `test_sound_cannotCancelNonexistentOrFutureVersion` PASS.
- Replay and duplicates: `award.paid` (`:190`, `:193`), `awards[id].actorId != 0` and `consumedSources` (`:145`), `id == awardId(sourceDigest)` with `chainid` and vault address (`:121-123`). Award ids differ across factories on the same chain for the same `projectId` because the CREATE2 address includes the factory address (`test_sound_factoryDuplicateAndCreate2` PASS).
- Integer bounds: all counters are `uint64` with checked arithmetic; every counter is bounded by `totalDeposited`, which cannot exceed `2^64-1` micro-USDC (18.4 trillion USD). `uint64(block.timestamp)` cannot truncate for ~5.8e11 years. `version + 1` (`:171`) would need 2^64 bindings. `expiresAt < block.timestamp` (`:169`) compares in `uint256`.
- Withdrawal fee: `floor((c+g)/10) - floor(c/10) <= g` for all `g >= 1`, so `gross - fee` never underflows; total fee equals `floor(cumulative/10)` independent of split (fuzz `test_sound_withdrawalFeeSplitInvariant` PASS, 256 runs); the `g == 1`, `c mod 10 == 9` case yields net 0 and `sendExact` returns early without revert (`test_sound_oneUnitWithdrawalCanBeAllFee` PASS).
- Conservation: both README identities hold after every tested sequence including `chargeService` (helper `conservationHolds` asserted in all state-changing tests). `payoutFee = gross/50 == floor(2%)`, matching `adapter.ts` `fee !== gross / 50n`.
- Role powers: authority cannot touch amounts, `freeBalance`, or paid awards (only `:159-175`); permissionless `pay` caller selects neither amount nor destination (`:187-201`); fee recipient blacklist blocks only `claimFees` while refunds and payouts continue (`test_sound_blockedDestinationLeavesReserve` PASS); blocked contributor destination leaves the reserve intact and `paid == false`.
- Factory: registrar-only `create` (`:285`), one vault per `projectId` (`:286`), no `selfdestruct` anywhere so no CREATE2 redeploy; constructor guards (`refundDestination == owner`, `owner != identityAuthority`, nonzero project id, six decimals, code present) verified by `test_sound_constructorGuards` PASS.
- Events: every money movement emits gross, net and fee where applicable (`Paid :72-80`, `UnusedWithdrawn :81`, `ServiceCharged :82`, `FeesClaimed :71`); `Paid` includes the binding version the adapter checks. No under-reporting found other than F-4's duplicate cancel event.
- Deploy scripts: chain-id pinned (8453 / 84532), no private key material, `envAddress` reverts when unset, Base mainnet USDC and fee recipient constants match the PRD (`docs/slop-product-requirements.md:814`) and `src/lib/fresh-cycle-policy.mjs:8`. `MIN_PRODUCTION_BINDING_DELAY` referenced by the README exists in `src/lib/escrow-policy.mjs:30` (48h) and is enforced in the manifest check there.

## Divergences between EVM and Solana

I did not review `lib.rs`; the following are from the brief's own description and need confirmation by the Solana reviewer.
- Fee delivery: EVM accrues fees and pushes them separately (`claimFees`), so a blocked fee recipient cannot block payouts. The brief says Solana transfers fees inside `pay`/`withdraw`/`charge_service` to a `fee_recipient`-owned token account; if that account is frozen, closed or wrong, Solana payouts stop while EVM ones continue. EVM has the stronger property.
- Binding scope: EVM bindings live in each vault's own `bindings` mapping, so a project-level authority compromise or owner veto affects one vault's routing. The brief says Solana `wallet` PDAs are seeded by `actor_id` only (shared across projects of the same authority and network). F-2's owner veto on Solana would then affect, or be contested by, other projects' owners; worth checking which owner can veto a shared wallet.
- F-1 applies to both if neither has an authority rotation path.

## Open questions for the lead

- Is F-1 accepted as a documented launch gate ("operational signer recovery") rather than a contract finding? My view: the README documents the redirect risk and the delay, not the no-recovery consequence, so it is at least a doc gap; the severity rests on how the authority key is custodied. If the key is a single hot EOA in a Slop service, I would keep High.
- F-2: is unbounded owner veto the intended product behavior? PAY-05 says "no expiry or sponsor reclamation of funded awards"; the owner cannot reclaim, but can hold forever. The README's "active binding is final" sentence is false under rotation plus cancel either way.
