# Reviewer: fable / Solana

Scope: `contracts/solana/programs/slop-escrow/src/lib.rs` at `main` bbcc87b, Anchor 0.32.1 (anchor-syn 0.32.2 in the lockfile), classic SPL Token only. `cargo check --locked -p slop-escrow` from `contracts/solana` finishes clean (two `unexpected_cfg` warnings from the Anchor entrypoint macro, no errors). No validator was run; every claim below is from the program source plus the generated Anchor constraint code in `anchor-syn-0.32.2/src/codegen/accounts/constraints.rs`, which I read to confirm the exact semantics of `init`, `init_if_needed` and `seeds`/`bump`. Line numbers below are `lib.rs` unless stated.

Summary: I found no Critical or High issue. The account model is tight: every account a transfer touches is pinned by a PDA derivation or a `has_one` back to the `Project`, the only transfer authority the program ever signs with is the project PDA over its own vault, and the veto / binding / obligation PDAs cannot be pre-created or re-initialized by anyone but the role the README names. The substantive findings are design-level: the 48 h veto window is measured from bind time, not award time, so it does not protect an award committed after a hostile binding has already activated (F-1); repeated vetoes give the owner an unbounded delay (F-2); and `binding_delay` has no upper bound (F-3). Everything else is Low or Informational.

## Findings

### F-1: Veto window is anchored to `bound_at`, so an award committed after a hostile binding activated pays instantly with no owner window
- Severity: Medium  Confidence: medium (mechanics high; severity depends on how far the lead reads the README's "an identity key can redirect future unpaid awards" as already covering this)
- Location: lib.rs:120 (`bound_at` set at bind), 157-160 (`pay` gate), 138-141 (`veto_binding` only while `now < bound_at + delay`), 293-297 (`activates_at`)
- Description: The brief's trust model says a stolen identity key is "mitigated by bindingDelay (48h) and the owner's cancel/veto during that window". The window is `[bound_at, bound_at + binding_delay)` and exists only once per binding version. Nothing ties it to when an award is committed. An attacker holding the identity key can bind (version 1, for an actor that has never claimed) or rotate (version n+1) an actor to a thief wallet, wait `binding_delay`, and only then wait for owners to commit awards to that actor. At commit time the binding is already active: `veto_binding` fails with `BindingActive` (line 138-141), and because `pay` is permissionless (no signer in `Pay`, line 401-420) the attacker submits `pay` in the same slot as the commit lands. The owner never had a window in which an award existed. Because bindings are shared across every project with the same authority and network (seeds at line 384 contain no project component), one pre-placed binding exposes every future award to that actor in every project.
- Scenario: (1) Attacker steals the identity key. (2) For actor 4242 (version 0, never bound) the attacker calls `bind_wallet(4242, network, 0, thief, any_digest)`. No award to 4242 exists, so no owner looks. (3) 48 h pass. (4) A month later project A commits `gross` to actor 4242. (5) In the same block the attacker calls `pay(1)` with `destination = ATA(thief)`. `activates_at` is in the past, the veto PDA is empty, so principal goes to the thief. Owner A's only tool, `veto_binding(4242, 1)`, reverts `BindingActive`. Slop can rotate to version 2 only after the fact.
- Evidence: reasoning only. The e2e test (`integration/escrow.e2e.mjs`) always binds after committing, so this ordering is untested.
- Recommendation: Give the owner a window measured from the award as well as from the binding. One shape: store `committed_at` in `Obligation` (set at line 75-83); in `pay` require `now >= max(binding.bound_at, obligation.committed_at) + binding_delay`; in `veto_binding` accept an optional unpaid `Obligation` for the same project and actor and allow the veto while `now < obligation.committed_at + binding_delay` even if the binding itself is already active. Alternatively document that the delay protects only awards that already exist when a binding changes, and that the owner (or the executor on its behalf) must read the current binding before committing. The EVM contract has the identical property (`activatesAt` fixed at `bindDestination`, `ProjectEscrow.sol:172`), so whichever fix is chosen should land on both.

### F-2: Repeated veto gives the owner an unbounded delay on a specific contributor's awards
- Severity: Low  Confidence: high
- Location: lib.rs:132-148 (`veto_binding`), 397 (`veto` PDA keyed by version), 119 (version increments monotonically)
- Description: Each new binding version opens a fresh `binding_delay` window and a fresh veto PDA. An owner can veto version n, wait for the authority to rebind as n+1, veto again, and so on. Each veto costs about 0.0009 SOL rent and emits `BindingVetoed`. The README says the owner "can delay a contributor's payout but never take an approved award back"; it does not say the delay is bounded. Reserved funds stay locked (the owner cannot withdraw them either), so this is mutual loss rather than theft, but the brief asks specifically about indefinite blocking. This is within the documented power applied repeatedly, so I rate it Low; the lead may treat it as Informational.
- Scenario: Owner commits an award to actor X, then vetoes every version the authority binds for X within each 48 h window. The award is never payable while the owner keeps vetoing. Nobody can recover the reserved `gross`.
- Evidence: reasoning only; e2e covers one veto followed by a successful rebind, not a second veto.
- Recommendation: Either state the unbounded delay explicitly in the README and PRD, or bound it in the program (for example: a veto is only accepted while the project has fewer than N vetoes for that actor, or a binding that is byte-identical in `destination` to a previously vetoed one for this project activates without a window after the second veto). EVM `cancelBinding` (`ProjectEscrow.sol:178-185`) has the same unbounded loop.

### F-3: `binding_delay` has no upper bound; `i64::MAX` (or any very large value) makes every award in the project permanently unpayable
- Severity: Low  Confidence: high
- Location: lib.rs:17-23 (only `binding_delay >= 0` is checked), 293-297 (`checked_add` returns `Arithmetic`), 157-160, 138-141
- Description: `initialize` accepts any non-negative `i64`. With `binding_delay = i64::MAX`, `activates_at` overflows for every binding, so `pay` and `veto_binding` both fail with `Arithmetic` forever. With a merely huge value (for example 10^10 seconds) `pay` fails `BindingPending` for 300 years. Funds the owner later commits are reserved and unrecoverable by anyone. This is the owner's own project and `adapter.ts:200` refuses a project whose stored delay differs from the reviewed manifest, so the realistic failure is a mis-typed manifest rather than an attack, but the program offers no floor against it and the committed money cannot be rescued.
- Scenario: Owner initialises with `binding_delay = 9_000_000_000`, deposits, commits awards (the commit path never reads the delay). Contributors bind. `pay` returns `BindingPending` until year 2311. `withdraw` cannot touch `reserved`.
- Evidence: reasoning only.
- Recommendation: Cap at initialise (for example `binding_delay <= 30 * 86_400`). The EVM side has the same gap (`uint64 bindingDelay_`, no cap, `ProjectEscrow.sol:102-116`; `uint64(block.timestamp) + bindingDelay` at line 172 wraps silently rather than reverting, which is worse: a wrapped `activatesAt` in the past makes the binding active immediately).

### F-4: `bind_wallet` accepts a zero `claim_digest`, a `destination` equal to the project or vault PDA, and has no submission expiry
- Severity: Low  Confidence: high
- Location: lib.rs:104-107 (only `actor_id > 0` and `destination != default` are checked), 412 (`pay` only excludes `destination.key() == vault.key()`, not an ATA owned by the vault or project PDA)
- Description: Three checks the EVM version has are missing here. (a) `claimDigest != 0` (`ProjectEscrow.sol:166`): on Solana a binding can carry an all-zero digest, so the executor's `hex(binding.slice(8,40)) !== input.claimDigest` comparison (`workers/payment-executor/solana.ts:508`) is the only thing giving the digest meaning. (b) `destination != address(this)` (`ProjectEscrow.sol:166`): on Solana the authority can bind an actor to the project PDA or the vault PDA; `pay` then transfers to `ATA(project_pda)` or `ATA(vault_pda)`, which passes line 412 because an ATA is never the vault address. The program has no instruction that signs for those ATAs, so the principal is stranded. This is inside the authority's documented redirect power but it converts a redirect into an unrecoverable burn. (c) `expiresAt` (`ProjectEscrow.sol:164,167`): a Solana bind transaction signed by the authority stays valid until its blockhash expires, or indefinitely if the relayer uses a durable nonce; only `expected_version` (line 113) bounds replay, so a stale signed bind for the current version can be submitted by whoever holds the bytes at any later time.
- Scenario (b): Compromised authority binds actor X to `vault` pubkey. Anyone pays. Principal lands in `ATA(vault, mint)`. Nothing can move it.
- Evidence: reasoning only.
- Recommendation: Add `claim_digest != [0;32]`, `destination != project.key()`, `destination != vault.key()` (the `Pay` struct cannot see it, so check in `bind_wallet` against the project passed in, or add `constraint = destination.owner != project.key() && destination.owner != vault.key()` on `Pay.destination`), and an `expires_at: i64` argument compared with `Clock` in `bind_wallet`.

### F-5: `initialize` does not require `fee_recipient != owner`; the program-level fee can be routed back to the owner
- Severity: Informational  Confidence: high
- Location: lib.rs:17-23
- Description: `identity_authority != owner` is enforced; `fee_recipient != owner` is not. A project initialised with `fee_recipient = owner` makes every `pay` fee, withdrawal fee and `charge_service` amount flow to a token account the owner controls (`fee_account.owner == project.fee_recipient`, lines 414, 431, 445). The program cannot know the correct recipient, and `adapter.ts:203` refuses a project whose stored `fee_recipient` differs from the reviewed manifest, so this is a manifest-review gate, not an on-chain one. Worth a one-line README note so a reviewer knows to check it.
- Evidence: reasoning only.
- Recommendation: Add `fee_recipient != ctx.accounts.owner.key()` to the line 17 `require!`, or state the manifest check in the README.

### F-6: Event fields are thinner than the EVM events
- Severity: Informational  Confidence: high
- Location: lib.rs:121-127 (`WalletBound` omits `authority` and `claim_digest`), 197-205 (`AwardPaid.destination` is the wallet owner, not the token account), 281-285 (`ServiceCharged` omits the fee token account)
- Description: The adapter deliberately reconciles from instructions and `postTokenBalances`, not logs (README, adapter.ts:400-430), so nothing breaks. Off-chain indexers that rely on events get less than their EVM counterparts (`DestinationBound` carries `claimDigest` and `activatesAt`, `ProjectEscrow.sol:68`).
- Evidence: reasoning only.
- Recommendation: Add `authority`, `claim_digest` and `activates_at`-equivalent (`bound_at` is there) to `WalletBound`; add the token account keys to `AwardPaid` and `ServiceCharged` if indexers will use them.

### F-7: Dead or redundant constraints
- Severity: Informational  Confidence: high
- Location: lib.rs:412 and 414 (`!= vault.key()`), 429 and 431, 445; lib.rs:71, 211, 262 (`vault.amount >= reserved + x`)
- Description: The SPL token program accepts a self-transfer (source == destination) as a no-op, so without the `!= vault.key()` constraints a transfer "to the vault" would succeed while the counters recorded a payment or fee. The constraints are therefore correct to keep. They are nearly dead in practice: `Pay.destination` must be the ATA of `binding.destination` (412), and an ATA address can never equal the vault PDA; `fee_account.owner == fee_recipient` could equal the vault only if the project were initialised with `fee_recipient` set to its own project PDA (derivable in advance), which the constraint then blocks. The `vault.amount >= reserved + x` checks (71, 211, 262) are implied by `free() >= x` for program-credited funds and only differ when unsolicited tokens sit in the vault, where `free()` is the binding check anyway. Mentioning so the lead does not count these as independent protections.
- Evidence: reasoning only.
- Recommendation: None required.

## Checked and found sound

- Account substitution on every `Account`/`UncheckedAccount`. `Account<'info, T>` for program types checks owner == program id and the 8-byte discriminator (`anchor-lang-0.32.1/src/accounts/account.rs:303-313`); `anchor_spl::token::TokenAccount` and `Mint` check owner == `spl_token::ID` (`anchor-spl-0.32.1/src/token.rs:458-462, 489-493`), so Token-2022 accounts and mints are rejected everywhere. `Program<'info, Token>` pins the classic token program on every transfer path (lines 346, 359, 416, 433, 449; `commit` makes no transfer and takes none).
- `project` is pinned in each instruction: `has_one=owner` on every owner-only path (352, 366, 393, 424, 440), `has_one=identity_authority` on `bind_wallet` (382), `has_one=mint` wherever a mint is used (352, 403, 424, 440); `commit` uses `vault.mint == project.mint` (368) instead. `pay` deliberately has no owner check (permissionless) and no `Signer` at all; nothing in `Pay` is attacker-selectable beyond the fee token account (any account owned by `fee_recipient`, line 414), and the adapter accepts any such account by reading `postTokenBalances.owner` (adapter.ts:426-428), so that choice cannot create reconciliation drift.
- `vault` is `seeds=[b"vault", project]` + `bump` (canonical, `find_program_address`, constraints.rs:1176) + `token::mint` + `token::authority=project` on every path (344, 357, 368, 410, 427, 443). Transfers always originate from `vault` signed with the project seeds (168, 219, 265), so the program can never sign for any other account.
- `obligation` in `pay`: `has_one=project` plus `seeds=[b"award", project, obligation.award_id]` (405). `binding` in `pay`: seeds use `project.identity_authority`, `project.network`, `obligation.actor_id` (407) plus three redundant field constraints. `veto` in `pay`: `seeds=[b"veto", project, obligation.actor_id, binding.version]` + `bump` on an `UncheckedAccount` still runs the `find_program_address` equality check (constraints.rs:1137-1200), so the address is pinned; the content check at 163-166 is `data_is_empty() && owner == system_program`.
- Veto pre-creation and lamport/assign tricks. The veto PDA can only gain data or a non-system owner through `allocate`/`assign` signed by the PDA, which only this program can do, and the only instruction that does so is `veto_binding` via `init` (397). `veto_binding` requires the binding to exist and `b.version == version` (135), so a veto for a version that does not exist yet is impossible; a future version can never be pre-blocked. Sending lamports to the veto address leaves it system-owned with empty data, so `pay` still passes. Anchor `init` on an address that already holds lamports takes the transfer+allocate+assign path (constraints.rs:1638-1676), so dusting cannot block `veto_binding`, `commit` (origin/obligation PDAs), `initialize` or a first `bind_wallet`.
- `init_if_needed` on `binding` (384): when the account is program-owned Anchor deserialises it (discriminator check) and additionally checks exact `space`, owner, and rent exemption (constraints.rs:1097-1127). Re-initialisation to version 0 is impossible because the handler requires `b.version == expected_version` (113) and a created account always ends with `version >= 1` (119); there is no close instruction, so the address can never return to system ownership. Only the identity authority can reach this path (`Signer` at 381 plus `has_one` at 382).
- A vetoed version can never pay: versions only increase (119), the veto PDA is permanent (rent-exempt, never closed, never debited), and `pay` uses the live `binding.version` for the veto seed (418) while requiring `expected_version` to equal it (154). An active binding cannot be vetoed (138-141). Veto and pay are disjoint on the same `Clock` value (`now < A` vs `now >= A`), so there is no same-slot ambiguity; Solana finality removes reorg concerns for the adapter.
- PDA seed collisions: the seven prefixes (`project`, `vault`, `award`, `origin`, `wallet`, `veto`, `service`) are pairwise non-prefix (`veto`/`vault` differ at byte 2), every seed component is fixed width (32, 32, 8, 8), and `award_id` is `sha256("slop-escrow-award" || project || source_digest)` (290-292), so awards are unique across projects, programs and chains.
- Reservation and conservation. `free()` (299-307) is `deposited - paid - payout_fees - withdrawn_gross - service_fees - reserved`; `commit` adds `gross` to `reserved` (74); `pay` removes exactly `principal + fee == gross` from `reserved` and credits `paid`/`payout_fees` (190-195); `withdraw` credits `withdrawn_gross` by `gross` while transferring `returned + fee == gross` (214-240); `charge_service` credits `service_fees` (276). Vault balance therefore always equals `free + reserved` plus unsolicited tokens, which `free()` ignores, so unsolicited deposits cannot be committed or withdrawn (e2e lines 530-536 cover this).
- Arithmetic: `fee = gross / 50 <= gross` (66-67); withdrawal `fee = floor(cum/10) - withdrawal_fees` is never negative and never exceeds `gross` because `withdrawal_fees` is always exactly `floor(prev_cum/10)` after each call (215-217, 240); every other addition is `checked_add`; u64 overflow needs 1.8e13 USDC. `binding_delay >= 0` (21) and `checked_add` in `activates_at` (294-296) prevent i64 wrap (see F-3 for the lock-not-wrap consequence). `transfer_checked` with hardcoded 6 is safe because `mint.decimals == 6` is enforced at `initialize` (342) and the mint is pinned by `has_one`/`token::mint` thereafter.
- `withdraw` destination: `token::mint=mint, token::authority=owner` (429) checks the token account's `owner` field equals the signing owner key. A delegate on that account is irrelevant (it cannot change the owner field), so "refund only to the declared owner" holds for the key; the owner may pick any of its own token accounts, unlike the EVM immutable `refundDestination`.
- `charge_service`: owner-only (`has_one=owner`, 440), free-funds-only (261-264), fee-recipient-only destination (445), exactly once per `(project, invoice_digest)` via the `service` PDA `init` (447), non-zero digest (256-258). It cannot reach `reserved`.
- `fee_account` frozen or closed cannot brick `pay`: any token account whose owner is `fee_recipient` and whose mint matches is accepted (414), and anyone can create a fresh one for that owner in the same transaction (the executor does, `solana.ts:560`). A frozen `destination` ATA reverts only that award (README, e2e 303-309). The one external brick is the issuer freezing the vault itself (see open questions).
- Duplicate account handles in one instruction (e.g. `destination == fee_account` when the authority binds an actor to `fee_recipient`): anchor-spl `TokenAccount` has a no-op `AccountSerialize` (token.rs:456), so stale cached state is never written back; both CPI transfers execute against live token program state.
- Roles 4 and 6: an owner of a different project with the same authority and network can only create vetoes keyed by its own project (397) and reserve its own funds; it cannot bind (needs the authority signer) and its veto does not affect other projects' `pay` (418 uses the paying project's key). The fee recipient has no instruction of its own and cannot prevent creation of new token accounts owned by its key.
- `initialize` griefing: the project PDA seeds include the signing owner (340), the vault PDA is derived from the project and created by the program (344); neither can be pre-created by a third party (a token account at a PDA needs the program's signature to allocate). `identity_authority != owner` is enforced (20).
- Replay: `obligation.paid` is permanent (196), no close instruction exists, so account recreation replay is impossible; `origin` PDA (370) makes a source digest commit once per project.
- Rent and payer roles: `bind_wallet` takes a separate `payer` so the authority never needs SOL (380); `veto_binding`, `commit`, `charge_service` are paid by the owner; `init` always funds rent exemption.
- Upgrade authority: documented launch gate; `deploy-testnet.sh` uses an isolated upgrade authority, refuses mainnet, and verifies the deployed ELF prefix. Nothing beyond the README.
- Deposit path: owner-only (352), `source` must be owner-owned (355), mint pinned, amount > 0.

## Divergences between EVM and Solana

- Binding scope: EVM `bindings[actorId]` is per vault (`ProjectEscrow.sol:173`); Solana bindings are shared per (authority, network, actor) across all projects (384), with per-project vetoes. A legitimate wallet rotation therefore opens a veto window in every Solana project at once, and a stolen key needs one bind per actor rather than one per vault. Documented in the README; noted here because F-1 compounds across projects on Solana only.
- Bind validation: EVM requires `claimDigest != 0`, `destination != address(this)` and `expiresAt >= block.timestamp` (164-167); Solana has none of the three (F-4).
- Delay bounds: neither caps the delay; EVM `uint64(block.timestamp) + bindingDelay` can wrap silently (172) while Solana reverts with `Arithmetic` (F-3).
- Fee delivery: EVM accrues fees and anyone pushes via `claimFees`; Solana transfers the fee inline in `pay`/`withdraw`/`charge_service` to any fee-recipient-owned token account chosen by the caller. Solana cannot be bricked by a bad fee account; EVM cannot be bricked by one either but `claimFees` can be blocked by a blacklist.
- Refund destination: EVM immutable `refundDestination`; Solana any token account owned by the owner key (429).
- Reserve accounting: EVM tracks `reservedPrincipal` and `reservedFees` separately; Solana one `reserved` (461). Conservation holds on both.
- `commit` input checks: EVM rejects `sourceDigest == 0` (143); Solana does not, harmlessly, because `award_id` is derived from it.
- Reentrancy: EVM needs `nonReentrant` and balance-delta checks; Solana's token CPI cannot call back into the program, so none is needed.

## Open questions for the lead

- F-1 severity: the README sentence "An identity key can redirect future unpaid awards" arguably documents the outcome, but the brief's own trust model presents the delay plus veto as the mitigation. I rated Medium on the "documented assumption that fails unsafely" rule; downgrade to Low if the lead reads the README as fully covering it.
- Issuer freeze of the vault token account (Circle blacklisting the project vault) locks `reserved` and `free` with no recovery path on either chain. Out of scope for the program but not mentioned in either README beyond destination freezes.
- `bind_wallet` with a durable nonce: does the executor/attester ever sign with a durable nonce? If so F-4(c) is live rather than theoretical.
- Existing e2e coverage gaps worth closing (all in `integration/escrow.e2e.mjs`): commit after a binding is already active (F-1 ordering); a second veto on the next version; two projects sharing the authority with different delays, verifying veto and delay isolation; `pay` with a non-ATA fee account owned by the fee recipient (accepted) and with an owner-owned account as `fee_account` (rejected); `veto_binding` for a version that does not exist yet; lamport dust at the veto, obligation and origin addresses before creation; `withdraw` to a non-owner token account; `deposit` by a non-owner; `initialize` with `identity_authority == owner`, negative delay, Token-2022 or non-6-decimal mint; an off-curve `destination`; a `gross < 50` zero-fee award; `claim_digest == 0`. The executor e2e initialises a second project sharing the authority and domain only to test scanner isolation, not veto or delay isolation.
